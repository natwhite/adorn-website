Contract-driven development for TypeScript

One declaration.
Every artifact.

Decorators adorn a function with its contract — what its inputs must satisfy, what has to hold before and after. Runtime enforcement, JSON Schema, documentation, tests and telemetry are all derived from that one declaration instead of maintained by hand, so they can't drift apart. An LLM tool schema is one of those derived artifacts, not the point.

Why adorn

Intent belongs with the declaration, not scattered around it.

A function's intent is usually spread across a check buried in the body, a schema in another file, a sentence in the docs and a hand-written test. Each one is maintained by hand, so each one drifts.

01 · DRIFT

Copies disagree

Raise a limit in the validator and forget the schema, and the schema promises one thing while the code enforces another. A drifted doc misleads a human who can compensate; a drifted tool schema silently corrupts every call.

02 · DATA

Constraints are data, not closures

@GreaterThanEqual(1) records an identity plus JSON-serializable params, and the predicate is derived from them. A schema keyword, a docs row, a fuzzer generator and the runtime check are all read from that one record.

03 · BOUNDARY

Enforced at every call

@Contract() wraps each contracted method, so a call with invalid arguments is rejected before the body runs. adorn validates and never coerces: a malformed argument is a violation, not something to quietly patch up.

This is contract-driven development

Declare what inputs are valid. Declare what must hold before the call, and what the function promises after. Then implement the body. The contract isn't documentation about the implementation — it's part of the program: enforced at the boundary, and read by every artifact that needs to know what the function expects.

How it works

Record, install, project.

A TypeScript parameter decorator runs once, when the class is defined, and never sees an argument value. adorn bridges that gap by splitting the work: decorators record descriptors, the class decorator installs enforcement, and projections read the same registry.

contractWhat must be true
↓  reified as data
descriptoran identity + JSON-serializable params
↓
enforcepre/postconditions · fields · boundaries
reason aboutinspect · compose · serialize
projectschemas · docs · tests · telemetry · tool APIs

The contract is the product. Everything below it is a consequence.

  1. DeclareParameter, field and method decorators, or plain descriptors with no decorator at all.
  2. RecordEach constraint is stored as a reified descriptor against (prototype, method, index).
  3. Install@Contract() runs after every member decorator and wraps each method with the recorded checks.
  4. ProjectDocs, schemas, tool schemas, telemetry and fuzzers all read the same registry.

JSON Schema 2020-12

schemaForClass describes what enforcement will accept. When unsure it falls back to the weaker true statement, because an over-claiming schema is worse than none.

Documentation

Markdown generated from the same statement that's enforced: documentClass → renderMarkdown, or adorn docs from the CLI.

core

Observability

A neutral, zero-dependency sink receives value-free violation and completion facts. adorn/otel maps them onto OpenTelemetry.

adorn/test

Property-based tests

fast-check generators derived from the contract. Generation is sound: it produces only inputs the contract accepts, or declines and says so.

The validator is the real guard

Run locally with no network: a bad nested date-time is rejected at ["when"], and so is a missing required field. Nullable(NotEmpty()) accepts null and still rejects "".

The tool schema, checked against a real provider

Because a machine produces malformed input the instant a schema is wrong, the tool-schema projection was round-tripped end to end through OpenAI's live function-calling API (gpt-4o-mini, temperature 0): schema accepted, tool call returned, its arguments validated against the same declaration — nested objects, nullable-optional fields and strict mode included. Evidence: docs/q31-capstone-results.md.

Beyond the decorator

Same descriptors, no decoration point needed.

Decorators are the ergonomic form, not the foundation. A raw unknown off the wire, a tool whose enum is known only at session start, or a codebase with no classes can use the same descriptors directly and get the same enforcement and projections.

BOUNDARY

Verify.check

Non-throwing. It narrows unknown to the constraint's output type and reports the failing path.

PER-SESSION

toolSchemaFrom

A runtime enum that no decorator could express. One const feeds both the schema and the validator.

ZERO CLASSES

contract(spec, fn)

The functional twin of @Contract, @Requires, @Ensures and @Returns. It's async-aware and runs the same oracles.

Design by contract, for stateful objects

Preconditions that read state, and a tester that respects them.

@Requires relates a call's arguments. @EnabledWhen also receives the instance, so "withdraw is enabled only while the balance covers it" is a declared contract instead of an if hidden in the body. fuzzSequence then drives generated call sequences against one evolving instance. It skips calls that aren't enabled yet and checks that invariants survive every transition.

What a clean run means

No generated sequence broke an invariant or a postcondition, which isn't the same as "correct". The tester samples rather than proves, and its report says so. A guard that throws instead of returning false is reported as a defect.

Honest project status

What works, what's rough, what's next.

adorn is a focused, deliberately narrow 0.1. This page aims to make its limits as easy to find as its features.

  • shipped
    Constraint vocabularyNumeric, string, formats, @OneOf/@Const, @ArrayOf, @Dictionary, @Shape, @Nullable, plus defineConstraint for your own.
  • shipped
    InheritanceField and method-parameter contracts are inherited. A subclass can strengthen a contract but never weaken it.
  • shipped
    Pre- and postconditions@Requires, @EnabledWhen, @Ensures, and the reified, projectable @Returns.
  • shipped
    Five in-core projectionsDocs, JSON Schema, LLM tool schema (including OpenAI strict mode), observability, and privacy review.
  • shipped
    Safe-by-default redaction@Sensitive / @Telemetry, plus a build-time sensitive-flow detector (adorn check).
  • shipped
    Add-ons as subpath exportsadorn/test (fuzzing, including fuzzSequence) and adorn/otel, each behind an optional peer.
  • rough
    Parameter names come from toString()Minification degrades names in docs and schemas, though enforcement and every projection degrade together.
  • rough
    Closures can't be projected@Requires, @Ensures and @EnabledWhen are enforced but invisible to docs and schema.
  • rough
    No constructor-parameter decorators yetValidate at construction with a @Validate() static factory instead.
  • rough
    Legacy decorators onlyThe decorator path needs experimentalDecorators (legacy TypeScript decorators, not the TC39 standard). No runtime metadata required; the descriptor-first path needs no flags.
  • next
    TC39 standard decorators adapteradorn/standard, recording into the same core model, so the paradigm survives the language's decorator transition.
  • next
    old() and constructor contractsPostconditions that reference pre-call state, and invariants established at construction. Both wait on evidence from real use.
  • next
    Format arbitraries for the fuzzerThe fuzzer currently declines on string formats rather than guessing.
  • next
    Add-on ecosystemResilience, rate-limit, idempotency, cache and policy decorators, deliberately kept out of core.

Reach for adorn when

  • you validate untrusted input at an HTTP or queue boundary
  • you want docs and privacy reviews that can't go stale
  • you want property-based tests derived from contracts you already wrote
  • you expose methods as LLM tools and need the schema and validation to agree

Don't assume yet

  • coercion or defaults injection, since adorn rejects and never transforms
  • per-request policy: configuration is process-level and set once at startup
  • proofs, because the fuzzer samples rather than proves
  • cross-checking against TypeScript types or TS default values
